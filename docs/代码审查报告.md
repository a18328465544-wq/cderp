# 代码审查报告

**项目**: 成都显卡一号店进销存管理系统 (GPU ERP)  
**版本**: 1.3.73  
**审查日期**: 2026-06-28  
**代码规模**: ~1707 行服务端路由 + 大量 store 逻辑 + 110 个前端组件文件

---

## 总体评价

这是一个**功能完整、架构清晰的进销存管理系统**，专门服务于二手显卡门店。代码整体质量良好，有完善的类型系统、权限控制、测试覆盖和错误处理。但也存在一些值得关注的安全隐患、架构扩展性问题和编码一致性方面的改进空间。

> 评级: **B+** — 生产可用，但存在需要修复（非紧急）的问题。

---

## 一、严重问题 (需尽快修复)

### 1.1 状态并发安全 — 内存写入与 DB 读取存在间隙

**位置**: `server/index.ts` — `persist()` 函数

```typescript
async function persist<T>(result: T, keys?: StateCollectionKey[] | null) {
  if (keys?.length) {
    await saveStateCollections(state, keys);  // 写入 DB
    return result;                            // ⚠️ 返回了旧 state 对应的 result
  } else {
    await saveState(state);
  }
  state = await loadState();  // 重新加载
  return result;
}
```

**问题**: 当 `keys?.length` 为真时，不走 `loadState()` 分支，返回的 `result` 引用的是写入前内存 state 对象。前端通过 `stateMerge/stateDelete` 合并时，如果该时间段内有其他并发写入，前端可能拿到不一致的数据。

**建议**: 统一在 `persist` 末尾始终调用 `loadStateCollections` 刷新受影响的集合，或将 `result` 与当前 state 重新关联。

### 1.2 缺少请求体输入验证

**位置**: `server/index.ts` — 所有 POST/PUT/PATCH 路由

```typescript
app.post("/api/purchase-invoices", requireMenu("purchase_add"), asyncRoute(async (req, res) => {
  const created = actions(req).createPurchaseInvoice(req.body);  // ⚠️ req.body 未经验证
  ...
}));
```

**问题**: 所有 API 端点直接将 `req.body` 传给 store 层，没有做任何 schema 校验或类型守卫。攻击者可以注入额外字段（如构造超长字符串消耗内存），或者传入不合法数据导致运行时异常。

**建议**: 引入最小化的验证中间件（如 zod），至少对价格、数量、ID 等关键字段做基础校验。

### 1.3 前端状态管理复杂度失控

**位置**: `src/utils/state.ts` — `useStoreState()` Hook

**问题**: 单个 Hook 包含 **22 个 useState**、多个 useRef、多个 useEffect、1000+ 行代码。每次状态变更触发整个 Hook 内部大量状态更新。虽然有 `KeepAlivePanel` memo 优化，但 `useStoreState` 本身是单一状态容器，任何集合的变更都会导致消费该 Hook 的所有组件重新渲染。

**建议**: 将大状态对象拆分为 context + useReducer，或使用 zustand 等轻量状态库管理分层状态。

### 1.4 服务端 store.ts 直接可变状态操作

**位置**: `server/store.ts` — 整个文件

```typescript
state.logs = [newLog, ...state.logs].slice(0, MAX_LOG_ENTRIES);  // 直接修改共享 state
state.inventory = state.inventory.map(...)
state.financeLedger = [ledgerItem, ...state.financeLedger];
```

**问题**: `createStoreActions` 接收的 `state` 参数是整个应用共享的引用。所有业务操作直接 mutate 这个共享对象，没有不可变性保证。如果有任何异步操作在修改过程中读取 state，可能读到中间状态。当前的 `saveQueue` 串行化缓解了这个问题，但不是根本解决方案。

**建议**: 在 `createStoreActions` 内部使用 draft 对象，操作完成后通过 `replaceState` 原子替换，或实现简单的写时复制。

## 二、中等问题 (建议近期修复)

### 2.1 Open API 敏感字段暴露

**位置**: `server/index.ts` — `openInventoryItem()` 函数

```typescript
function openInventoryItem(card: AppState["inventory"][number]) {
  return {
    costPrice: card.costPrice,    // ⚠️ 成本价暴露给了外部 API
    estSellPrice: card.estSellPrice,
    ...
  };
}
```

**问题**: Open API 没有实现与内部 API 相同的脱敏逻辑（`publicStateForUser` / `sanitizeInventoryRowsForUser`）。如果合作方 API key 泄露，所有成本数据将直接暴露。

**建议**: Open API 默认不应返回 `costPrice`，或增加一个显式的可选参数 `?includeCost=true`。

### 2.2 采购/销售开单缺少事务性保证

**位置**: `server/store.ts` — `createPurchaseInvoice` / `createSalesInvoice`

**问题**: 创建单据过程涉及多步 state 操作（创建单据 → 生成库存 → 更新客户统计 → 写入财务流水 → 调整账户余额），但没有任何事务回滚机制。如果中间某步 throw error，前面已经修改的 state 不会回滚。

**建议**: 在 store 层引入简单的 snapshot/rollback 机制，或在关键操作前 clone 相关集合，操作失败时还原。

### 2.3 前端全量计算统计指标

**位置**: `src/utils/state.ts` — `getAccountSummary()` / `getInventorySummary()` / `getCrmSummary()`

**问题**: 财务汇总、库存汇总、CRM 汇总全部在前端通过 `Array.filter/map/reduce` 遍历全量数据完成。当前数据量小没问题，但数据增长后会成为性能瓶颈。尤其是 `getAccountSummary` 每次都重建整个 `employeeMap`。

**建议**: 将统计汇总改为后端接口 + 分页返回，前端只做展示。

### 2.4 路由匹配使用字符串前缀

**位置**: `server/requestStatePolicy.ts`

```typescript
if (startsWithAny(path, ["/api/purchase-invoices"])) return PURCHASE_KEYS;
```

**问题**: 使用 `startsWith` 进行路由匹配，`/api/purchase-invoices-test` 也会匹配到 purchase 的持久化策略。虽然当前 API 设计不会出现冲突，但不够严谨且难以维护。

**建议**: 使用精确路径 + 参数化路由匹配，或引入 Express Router 的中间件模式。

### 2.5 密码兼容明文存储

**位置**: `server/security.ts` — `verifyPassword()`

```typescript
export function verifyPassword(storedPassword: string | undefined, inputPassword: string) {
  if (!storedPassword) return false;
  if (!isPasswordHash(storedPassword)) {
    return storedPassword === inputPassword;  // ⚠️ 明文比较（旧数据兼容）
  }
  ...
}
```

**问题**: 为了兼容旧数据的明文密码，允许明文比较。虽然这是过渡方案，但应该有一个明确的迁移截止时间和日志告警。

**建议**: 当检测到明文密码匹配时，自动将其升级为 hash 存储，并记录审计日志提醒管理员。

## 三、轻微问题 (可择机优化)

### 3.1 重复代码

- `sanitizeAppStateForClient` 和 `publicStateForUser` / `publicCollectionForUser` 中存在大量重复的脱敏逻辑
- 采购/销售单据的 merge 函数模式高度相似，可提取通用工厂函数
- 22 个集合的 `applyServerStateMerge` / `applyServerStateDelete` 都是机械重复代码

### 3.2 演示数据硬编码

**位置**: `server/store.ts`

系统初始化数据（用户、结算账户、财务流水）分散在 `store.ts` 和 `demoData.ts` 中，环境切换不直观。

**建议**: 统一到 seed 脚本或环境变量控制的初始化流程。

### 3.3 TypeScript 严格模式未启用

**位置**: `tsconfig.json`

当前 TS 配置未启用 `strict: true`，可能导致隐式 `any` 和未检查的 null/undefined 访问。

### 3.4 错误处理不够细化

- 很多 catch 只打印 `console.warn`，丢失了错误上下文
- 删除操作失败后没有区分"不存在"和"权限不足"
- 财务计算中的 `Number()` 转换可能静默产生 NaN

### 3.5 日志表无限增长风险

虽然代码中有 `MAX_LOG_ENTRIES = 10000` 的上限，但 `appendOnlyCollection` 只做增量追加，数据库中可能有超过 10000 条的旧日志。当内存 buffer 被截断时，DB 中的多余行会在 `deleteMissing` 阶段被清理，但这个过程可能产生大量 DELETE。

### 3.6 前端未处理 `NaN` 显示

`getInventorySummary` 中 `avgCost = Math.round(totalCost / totalCount)`，如果 `totalCount` 为 0 会产生 `NaN`（虽然实际不会发生，但缺少防御性编程）。

## 四、架构层面评价

### 优点

| 方面 | 评价 |
|------|------|
| 类型系统 | ★★★★★ — `types.ts` 完整定义了 700+ 行业务类型，前后端共享 |
| 权限模型 | ★★★★☆ — 角色 + 菜单 + 字段级脱敏，设计合理但实现有重复 |
| 持久化策略 | ★★★★☆ — JSONB 集合表 + 增量 upsert + 写锁，适合单实例场景 |
| 测试覆盖 | ★★★★☆ — 22 个测试文件覆盖核心业务逻辑 |
| 前端性能优化 | ★★★★☆ — chunk 分割、懒加载、KeepAlive、autoSync 防抖 |
| 安全基础 | ★★★☆☆ — helmet + 限流 + 密码哈希 + 会话管理，但缺少输入验证 |

### 架构演进方向

1. **拆分 store.ts** — 当前所有业务逻辑集中在一个巨大文件中，应按领域拆分为 purchase-service / sales-service / finance-service
2. **引入 API Schema 校验** — 使用 zod 或 typebox 做请求/响应校验
3. **前后端通信协议标准化** — 当前 `ok()` / `okMerge()` / `stateDelete` 三种响应模式自定义过多
4. **数据库索引优化** — JSONB 查询依赖全表扫描，应为 `(data->>'sn')`、`(data->>'productId')` 等高频查询字段加 GIN 索引或生成列
5. **会话持久化** — 当前内存会话在 PM2 重启后全部丢失，应迁移到 Redis 或 DB

## 五、总结

| 类别 | 数量 | 风险 |
|------|------|------|
| 严重问题 | 4 | 中-高 |
| 中等问题 | 5 | 中 |
| 轻微问题 | 6 | 低 |

**整体评价**: 这是一个成熟的、在实际门店中跑起来的系统。代码风格一致，业务建模清晰，权限和审计体系完整。主要风险集中在**并发安全**和**输入验证**两个维度，在单用户/低并发场景下不会暴露，但随着用户数增加和 API 对外开放，需要优先加固这两个方面。

**优先修复建议**:
1. 增加请求体输入验证（低成本，高收益）
2. 修复 `persist()` 的 partial keys 路径不刷新 state 的问题
3. Open API 默认脱敏成本价
4. 将明文密码自动升级为哈希存储
