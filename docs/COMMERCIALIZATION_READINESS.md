# GPU ERP 商业化收口报告（P0–P2）

日期：2026-08-29
分支：`codex/frontend-v2`
范围：在不改变采购、销售、库存和财务业务语义的前提下，补齐商业化运行所需的租户边界、账号生命周期、可靠性门禁、配额和运营控制面。

这份报告把“代码已具备”与“部署环境仍需完成”分开。通过类型检查、测试或构建，不等于已经完成生产部署、真实数据库迁移、浏览器验收或异地恢复演练。

## 1. P0：数据边界、权限和账号生命周期

已落地：

- `gpu_tenants`、`gpu_stores`、`gpu_tenant_memberships` 建立企业、门店和成员关系；业务集合、会话、媒体关系均带租户/门店作用域。
- 请求认证先解析会话作用域，再执行租户状态和成员关系校验；暂停、归档企业不能继续访问业务数据。
- `POST /api/commercial/context/switch` 轮换会话并校验目标企业/门店成员关系，旧令牌随后撤销。
- 老板可通过 `/api/users/:id/deactivate`、`reactivate`、`reset-password` 管理账号；停用账号会撤销其会话，席位上限在成员写入和重新启用时检查。
- 新企业必须绑定一个显式启用的负责人账号；停用或缺少 `enabled=true` 的账号会被拒绝。
- 审计日志保持追加式；兼容清空接口返回冲突，不再物理清空证据。
- 生产预检检查核心租户表、会话、媒体、检测版本、每日结算表和硬化迁移版本。

边界说明：现有 `gpu_system_users` 仍兼容历史 JSONB 账号表，跨企业共享身份的完全规范化用户表尚未替换。当前企业切换依赖成员关系和全局 ID 解析；在启用大量跨企业账号前，需按 [COMMERCIALIZATION_API_GAP.md](./COMMERCIALIZATION_API_GAP.md) 完成身份表迁移。

## 2. P0：业务一致性和恢复能力

已落地：

- 采购、销售、出库、退货和关键财务写接口继续经过状态 mutation runner 和 PostgreSQL 事务。
- 采购、销售、出库、退货已有租户级幂等键；本轮为结算账户、收款、付款、资金调拨新增相同的 `Idempotency-Key` 重放保护。
- 出库库存占用写入 `gpu_inventory_reservations`，活动卡唯一约束阻止重复占用。
- 每日通知和日结快照主键升级为 `(tenant_id, store_id, date/notification_type)`，多门店不再互相覆盖。
- 检测记录追加 `gpu_inspection_versions`，保留历史版本证据。
- 登录/退出使用独立认证写锁，不和业务状态写锁混用；会话定期清理过期令牌。
- 备份、恢复演练、就绪探针和单实例 PM2 拓扑继续由现有脚本和 systemd 模板约束。

## 3. P1：查询、媒体和运营效率

已落地：

- 库存、日志、采购/销售单据、资金流水和提成列表支持服务端分页、过滤、排序和租户/门店条件。
- 高频查询使用 operational projection 和索引；`check:performance` 持续检查首屏和图表 chunk 预算。
- 媒体上传校验 MIME、输入大小、压缩后大小、租户隔离和媒体额度；同租户相同 SHA-256 复用资源，关系读取始终带租户条件。
- 套餐控制面支持 pilot/standard/pro/enterprise，席位、媒体和 AI 用量以数据库行锁和当前周期额度校验。
- 功能开关会同时校验企业状态、订阅状态、试用期、计费周期和 `past_due` 限制，未知能力默认关闭。
- 老板可申请租户数据导出，导出文件按租户目录隔离，并对 CSV 公式前缀做防注入处理。
- 预检新增幂等键、库存占用、检测版本、每日结算和运营索引的检查。

仍需外部/后续配合：产品候选接口仍保留兼容的整集合语义；媒体孤儿回收、超大 JSONB 分片和正式的异步导出队列属于下一轮后端能力，见 API Gap。

## 4. P2：套餐、支持和生态能力

已落地的内部基础：

- 订阅和用量表、席位/媒体/AI 配额、套餐功能白名单、租户导出记录、诊断计数和请求 ID/低基数指标。
- CI 已包含前后端类型检查、静态架构检查、测试、构建、性能预算、依赖审计和 Docker 数据库集成测试入口。
- 生产预检输出 `PASS/FAIL`，覆盖密钥、迁移、核心表、索引、密码哈希、备份新鲜度和构建产物。

商业化上线仍需部署方完成：

1. 选择并接入支付/订阅提供商，配置 webhook 签名校验、重放保护、退款/欠费状态同步；当前代码不伪造支付成功。
2. 配置真实错误追踪和告警接收端，将 `X-Request-Id` 与操作日志、发布版本关联；本地日志接口不是外部告警平台。
3. 配置对象存储或异地备份目标，并完成独立数据库恢复演练和证据留存。
4. 如需企业 SSO、SCIM、外部库存/电商/物流集成，先完成供应商安全评审和租户级凭据保管，再启用对应套餐能力。
5. 多副本、多区域部署前，先替换进程内读投影、会话和缓存为共享实现；当前生产拓扑仍必须是单个 PM2 fork。

## 5. 迁移和发布顺序

1. 在生产副本执行 `001_crm_foundation.sql`、`002_operational_projections.sql`、`003_crm_foundation_v2.sql`、`004_commercial_foundation.sql`、`005_commercial_hardening.sql`，记录每步行数和索引结果。
2. 配置 `DATABASE_URL`、`DATABASE_SSL`、`POSTGRES_IMPORT_LEGACY_JSON=false`、`OPEN_API_TOKEN`、`BOOTSTRAP_ADMIN_PASSWORD`、备份和异地目标。
3. 在独立库执行 `RESTORE_DRILL_CONFIRM=I_UNDERSTAND_ISOLATED_DATABASE npm run restore:drill`。
4. 运行 `NODE_ENV=production npm run preflight:production`、`/api/ready`、真实测试账号权限和关键只读/受控写操作验收。
5. 确认备份、监控、回滚负责人后，才执行发布流程；本次代码变更本身不触碰生产数据库。

## 6. 本轮代码证据

- 服务端严格类型、服务端测试类型、架构和 mutation route 检查已通过。
- 商业 schema、租户查询作用域、密码升级作用域、套餐边界和生产预检脚本均有单元测试。
- 详细命令结果以交付消息为准；若 Docker、真实数据库或生产凭据不可用，必须标记为未执行，不能用本地构建替代。

## 7. 结论

P0/P1 的代码级隔离、幂等、配额、查询和运维门禁已纳入当前分支；P2 的内部控制面已提供，但支付、外部告警、异地备份、SSO 和多区域仍是部署/供应商前置条件。当前可称为“商业化候选版本”，不能在未完成真实环境预检、备份恢复和专用账号验收前宣称已完成最终生产上线。
