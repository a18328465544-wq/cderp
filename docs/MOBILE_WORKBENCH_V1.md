# 移动工作台 V1

2026-10-07。本轮是本地前端实施，不包含生产发布。

## 范围与边界

- 手机（小于 768px）采用独立的任务型展示：工作台、库存、开单、单据、更多。入口、名称与权限来自现有导航契约。
- 平板（768–1023px）保持工作区和主从视图；电脑（1024px 起）保持表格。明细表内部横向滚动，不撑宽整个页面。
- 共用当前路由、查询、表单控制器、校验规则与写接口；不修改账务、库存、退货、金额和幂等语义。
- 仅保活已打开任务，不预加载未打开页面，Tab 上限仍为 10。录单内容和当前步骤在普通切换后保留；关闭或淘汰有修改的任务仍需确认。
- 当前草稿属于已有工作区生命周期，不承诺关闭浏览器、刷新或系统杀进程后恢复；没有新增离线财务写入或自动补交。

## 手机体验

1. 工作台首屏优先销售/采购开单，然后是待办及已有录单草稿；手机不加载桌面 AI 图表。底部开单入口持续突出。
2. 库存、采购、销售、客户、供应商及退货列表使用现有 DataTable 的卡片投影。搜索直接显示，高级条件进筛选面板，列表设置另开面板；统计默认收起。
3. 销售、采购按客户/来源 → 商品 → 结算分步。同一张表单所有字段保持挂载；仅隐藏非当前步骤。中间步骤按回车不会提交业务单据。
4. 商品明细只展开当前编辑项，已录商品可收起；空闲的默认四行按需启用，电脑仍显示四行。
5. 全新/配件质检保留简易流程；二手 GPU 按 SN → 实测 → 确认分步，确认前展示商品、SN、成色、库位和实测数据摘要。校验和上传状态仍由原表单负责。
6. 出库先选单再核验。返回列表再打开同一单保留扫码，选择不同单不会沿用上一单扫码。
7. 采购退货按商品 → 结算预览 → 原因确认；销售退货按原单 → 商品 → 原因确认。单件、多件、整单的可用范围不变。
8. 短确认居中、小选择底部面板、大表单全屏。层级和关闭行为复用现有 Dialog/Drawer/Picker。
9. 更多采用常用功能分组列表，而非桌面菜单全量平铺。组装批量管理、商品配置、员工权限、日志、备份、月结等入口留在桌面；不改变这些路由和后端权限。
10. 库存扫码与搜索并列，复用已有摄像头识别窗口，仅回填当前搜索条件，不自动入账或修改库存。浏览器不支持识别时保留手工 SN 搜索。

## 设计参照

- Shopify Mobile：借鉴订单、库存和移动业务操作的组织方式，不照搬其商品/账务模型。https://www.shopify.com/mobile
- Linear Mobile：常见任务优先、克制的层级和列表；手机是电脑工作区的延伸。https://linear.app/docs/get-the-app
- Square Retail：借鉴搜索和扫码易触达、识别后确认的操作习惯。https://squareup.com/help/us/en/article/7992-automate-item-creation-with-square-for-retail
- 本系统依然围绕型号、单件 SN、成色、质保及来源单据追溯；未新增扫码自动盘点、离线开单或独立账务模型。

## 共享规范

- 新增参数及手机高度统一放入 tokens.css；字体、颜色和金额格式继续沿用现有系统。
- 手机可见主要操作触控高度至少 44px，输入文字 16px，避免 iOS 输入自动放大。
- 固定操作区预留底部导航和安全区；软键盘出现隐藏底部导航。统一视觉视口计算区分“只缩视觉视口”和“布局也缩小”，避免键盘高度重复扣除。
- 手机步骤仅做展示和校验结果消费，不建立第二套 DTO、状态机或计算规则。

## 验证

- scripts/browser-mobile-workbench.py：仅允许 localhost，所有 API 使用拦截数据，覆盖 320/360/390/430/768/1024/1440px 的导航、筛选、录单草稿、失败重试、回车保护、全新/二手检测与出库；390px 额外覆盖采购单件/多件/整单与销售单件/整单退货的失败、幂等重试、成功重置。
- scripts/browser-order-submission.py、scripts/browser-return-submission.py：电脑端原流程的成功、失败、重复提交及异步归属回归。
- npm run lint、npm test、npm run build 和性能预算继续使用项目门禁。
- 浏览器宽度模拟不是实体手机验收。发布前仍需真机验证 iOS Safari/Android Chrome 的软键盘、摄像头、浏览器工具栏和安全区。
