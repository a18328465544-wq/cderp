## 一、本轮修复的缺陷(P0/P1)

| 级别 | 问题 | 影响 | 修复 |
|---|---|---|---|
| P1 | 销售单成本/毛利信任客户端传入的 `costPrice` | 无 `showCost` 权限的销售开单会传入 0,导致毛利虚高、账目失真 | `createSalesInvoice`/`updateSalesInvoice` 改为从库存卡 `card.costPrice` 读取**权威成本**,逐项重算 `profit` 与单据合计 |
| P1 | 主键用 `Date.now()` 生成,同毫秒批量写入会碰撞 | 销售单、用户、客户等主键重复,`map(id===x)` 误更新/串单 | 新增 `genId()`(时间戳+进程内自增计数器),替换所有裸 `Date.now()` 主键 |
| P1 | 单据序号 `seq = 列表长度 + 1` | 删单后序号回退,产生**重复单号** | 新增 `nextDailySeq()`,按当日已存在单号最大值 +1 |
| P1 | SN 唯一性校验分散且采购单完全缺失校验 | 采购录入可写入重复 SN,污染库存唯一性 | 集中为 `findCardBySn()`/`assertSnUnique()`;采购单新增“批次内+全库”双重校验 |

涉及文件:[server/store.ts](../server/store.ts)、[server/db.ts](../server/db.ts)、[server/index.ts](../server/index.ts)。

## 二、SN 唯一性校验

序列号代表唯一实物显卡,必须全库唯一(大小写不敏感,空 SN 表示未绑定)。统一后覆盖全部绑定入口:

- **采购录入** `createPurchaseInvoice`:批次内去重 + 与现有库存冲突检测。
- **质检入库** `submitInspection`:绑定 SN 时校验全库唯一(排除自身)。
- **扫码入库** `scanInventoryFlow`:重复 SN 返回“该SN已存在,不能重复绑定”。
- **组装/拆卸** `createAssemblyOperation`:拆后配件批次内去重 + 全库冲突;组装后 SN 全库唯一。
- **批量导入** `importInventoryRows`:导入模型本身不含 SN 字段(批量入库不绑定 SN),无唯一性风险。

校验逻辑统一收敛到 `findCardBySn`/`assertSnUnique`,后续新增入口直接复用,避免再次出现遗漏。

## 三、入库 / 出库流程测试

测试位于 [server/store.test.ts](../server/store.test.ts),覆盖完整链路:

**入库链路**
- 采购录入 → 生成“待检测”库存卡 → 质检绑定 SN → 状态流转“已入库/维修中/已退货”,库位、成色、保修同步更新。
- 按快递单号先登记、检测时再绑定 SN 的两段式入库。
- 非显卡配件走简易检测后入库。
- **新增**:质检绑定已被占用的 SN 时正确抛出 `SN已存在`。

**出库链路**
- 销售开单先锁定库存(`已锁定`)→ 扫码/手动确认出库(`已售出`)→ 商品库存数、客户成交、财务流水同步。
- 扫码不全时拒绝出库;重复/不可售库存卡被拒绝。

**防重号**
- **新增**:删除早期单据后新建单据,单号基于当日最大序号 +1,确保现存单号集合无重复。
- **新增**:连续快速创建 50 张单据,主键全部唯一。

## 四、毛利计算校验

- 公式:`毛利 = Σ售价 − Σ成本`,成本一律取自库存卡权威成本。
- **新增测试** `gross profit always uses the authoritative inventory card cost`:即使客户端传入 `costPrice=0`,单据成本/毛利仍按库存卡真实成本计算。
- 导出与汇总中的成本/毛利列受 `showCost` 权限控制(见下)。

## 五、数据导出

新增服务端 CSV 导出端点 [server/export.ts](../server/export.ts):`GET /api/export/:dataset`,支持 `inventory / sales / purchases / ledger / customers`。

- UTF-8 BOM 输出,Excel 直接打开中文不乱码;字段统一 CSV 转义。
- **权限控制**:`showCost=false` 的角色(如检测员)导出时自动隐藏“成本/毛利”列,防止越权获取利润数据。已端到端验证(检测员导出无成本列,店员/老板有)。
- 单元测试 [server/export.test.ts](../server/export.test.ts):转义、列裁剪、全数据集、非法数据集 5 项全过。
- 前端各模块原有的库存/商品/结算 CSV 导出保持不变。

## 六、备份方案

实现于 [scripts/pg_backup.sh](../scripts/pg_backup.sh) 和 [server/db.ts](../server/db.ts):

- **数据库自动备份**: `pg_dump --format=custom` 生成 PostgreSQL dump,由
  `ops/systemd/gpu-erp-backup.timer` 每日 03:20(Asia/Shanghai)触发。
- **完整性校验**:备份完成后执行 `pg_restore --list`,通过后才原子移动到备份目录。
- **保留策略**:默认保留 `BACKUP_RETENTION_DAYS=30` 天的 `gpu_erp_*.dump` 文件。
- **手动业务快照**:`POST /api/backup`(老板权限)用于人工核对、迁移和应急留档。
- **恢复演练**: [scripts/pg_restore_drill.sh](../scripts/pg_restore_drill.sh) 要求显式确认隔离数据库,
  并拒绝与 `DATABASE_URL` 相同的目标。
- **异地备份**:备份目录应位于应用目录外,并同步到异地或对象存储。

## 八、已处理的基础风险

1. **请求级鉴权与限流**:登录接口已有限流,开放 API 使用独立 token 和限流;业务路由仍由服务端菜单权限校验。
2. **数据库主库**:PostgreSQL 已替代 JSON 文件作为生产主库,JSON 文件仅作为受控历史导入来源。
3. **会话持久化与清理**:`gpu_sessions` 只保存 token 哈希,支持 PM2 重启和多实例共享；活跃会话流量会按统一间隔批量清理过期记录，清理失败不阻断登录或鉴权。
4. **敏感字段**:用户密码哈希、成本和权限字段通过服务端投影控制;前端隐藏不作为安全边界。
5. **可观测性**:请求 ID、脱敏错误日志和老板权限 `GET /api/ops/metrics` 已覆盖请求量、5xx 与延迟；指标路由不保存查询值、用户 ID 或凭据。
6. **生产环境**:`POSTGRES_IMPORT_LEGACY_JSON=false`;增量迁移 `operational-projections-v1`
   已应用，共核验 28 个 `op_*` 投影字段；生产和预发布 PM2 进程均在线。
7. **备份与恢复**:发布前备份 `gpu_erp_20260823-211152.dump`、迁移后备份
   `gpu_erp_20260823-212348.dump` 均为 1.4MB 且通过 TOC 校验；后者已恢复到通过
   SSH 回环隧道连接的一次性 PostgreSQL 16 容器，核心行数指纹
   `311:203:99:318:4` 一致，演练容器随后删除。
8. **服务器门禁**:`gpu-erp-backup.timer` 已启用并处于 active，手工触发服务结果为
   success；Nginx 配置检查通过，SPA、静态资源与 API 均返回受控安全头。
9. **剩余运营风险**:需要指定异地备份接收端；生产没有专用测试账号，现有初始化密码
   已被修改，因此没有重置真实账号来强行完成鉴权验收。
