# 收付款与退货依赖回归边界

## 退款不是可独立改动的其他收支

- 待处理和已完成、未作废退货的退款分摊保护原收付款。独立冲销被引用的原收付款返回冲突，账户、原单、退货、库存、两套流水和日志保持原样。
- 缺少分摊的历史退货按原单稳定编号/单据号关系及原路退款/实际现金释放事实保护；不用模糊姓名或编号前缀猜测归属。
- 退货生成的收退款只能由所属退货反向流程撤销。内部 `owningReturnId` 能力只由退货领域传入，HTTP DTO 不开放；`skipInvoiceUpdate` 和其他退货编号不构成绕过授权。
- 原路退款分摊排除作废、草稿或未入账原流水。存在这类历史原流水时不能借人工账户回退再次释放现金；真正缺失历史流水的既有显式人工账户兼容仍保留。
- 已结案售后维修费/退款不能从普通付款冲销入口拆掉，以免工单仍保留收费事实。当前没有新增售后冲销页面或自动历史更正能力，需要另行设计所属业务的更正流程。
- 原单存在待处理或已完成退货时，不允许结构、往来对象、商品及结算字段修改；检查发生在任何账务修改之前。合法备注等元信息编辑保持原有行为。
- 作废的收款、付款和资金调拨不能再次编辑；普通收付款编辑不能补绑原业务单据，必须走所属单据流程。

## 增量持久化与权限是两条独立边界

`captureFinanceFacts` 在已有写锁内捕获当前门店三类资金事实的值；`completeFinancePatch` 补充原业务补丁漏掉的变化，不整表覆盖：

- 收付款改账户时同时保存旧、新账户。
- 补录早期流水、修改时间/金额或移除流水时保存所有发生变化的后续账户余额链。
- 调拨换账户时保存受影响的原、现账户，冲销使用动作前的流水编号派生删除补丁，避免删除后再查得到空集合。
- 仍调用既有增量保存与幂等事务，完整金额/流水保存在数据库和内部幂等回执中。

采购、销售的新建/编辑/删除，退货的新建/完成/编辑/作废/冲销/删除，以及售后的新建/结案更新，现在也使用同一资金差量逻辑。`runFinanceStateCommand` 包装既有 `runStateCommand`，保留附件准备、CRM 同步、库存预留释放和幂等回执的原事务边界；保留手工持久化钩子的删除/冲销入口在动作前捕获事实，再补全原业务补丁。已入账单据的删除保护没有放宽。

本轮失败测试证明原来的“只保存与当前单据相关的流水”不够：换账户会漏掉旧账户的新余额，退货退款或维修费会漏掉时间更晚、与当前业务单据无关的流水余额。修复同时保存这些受影响的行，但不修改无关账户。

12 个收款、付款和调拨写入口及其成功重放统一在 HTTP 边界调用 `projectFinanceMutationResponse`。当前账号权限决定 `data`、`stateMerge` 和 `stateDelete` 的可见性；旧缓存的全状态、系统账号或任意附加集合不透传。权限收回不会改写数据库金额，也不会重复执行命令。内部完整资金事实不能因为响应脱敏而被保存成零。

采购/销售的 6 个写入口及重放使用 `projectInvoiceMutationResponse`；退货和售后继续使用各自业务投影。新增加的后续流水补丁不能绕过当前账号的资金菜单、成本或利润权限。删除补丁仅保留允许的集合，并且单据删除只能指向当前响应对应的本类单据；旧缓存中的另一类单据删除和系统账号信息不透传。售后的资金删除补丁同样按当前权限投影，不删除库存/销售单等任意附加集合。

支付写请求显式加载退货/售后校验依赖，但不把这些只读依赖加入持久化集合。当前写路径仍在原有锁内加载业务状态，并按三类资金集合的完整值快照比较差量；本轮没有改为定向 SQL 命令仓库，也不宣称大账本的写入性能已经完成优化。

## 可重复验证

- `server/storePaymentDependencies.test.ts`：采购/销售退款来源、待处理原单保护、历史编号兼容、作废来源和所属反向能力；拒绝分支比较完整状态。
- `server/storeAftersalesAmounts.test.ts`：维修收费事实不能被普通付款冲销拆开，原维修结案回归保持执行。
- `server/financeMutationPatch.test.ts`：把增量补丁重新应用到动作前状态，逐条比较账户、账户流水、财务流水与动作后事实；并证明旧补丁遗漏确实会导致不一致。
- `server/routes/financePayments.test.ts`：12 个入口成功重放都重新投影，内部缓存保持原样。
- `server/invoiceMutationResponse.test.ts`：采购/销售正常响应和 6 个入口的旧缓存重放，验证成本/利润脱敏、资金集合可见性、非法删除补丁隔离及完整内部事实不变。
- `server/aftersalesResponse.test.ts`：售后资金删除按当前权限裁剪，旧缓存与完整内部事实不变。
- `server/httpIntegration.test.ts`：一次性本地 PostgreSQL、真实 Cookie/CSRF 登录、换账户、补录早期流水、调拨移账户/冲销后 SQL 读取、作废编辑拒绝和同一会话权限收回后的重放；原出库冷快照与退货测试继续执行。新增 9 个跨业务 SQL 场景覆盖采购/销售新建和换账户、采购/销售各自单件与整单退款及冲销、售后维修费；每个资金场景都加入时间更晚的无关流水并逐条核验余额链，重复请求后再次读取 SQL 确认没有二次入账。

普通完整测试环境不配置数据库，因此 HTTP 场景标记跳过；`npm run test:backend-http:docker` 单独运行所有数据库场景，结束自动清理本地容器。浏览器出库测试使用本地模拟接口，只证明交互，不替代数据库/生产验收。

本轮未连接生产、未部署、未迁移或更正历史流水，未提交或推送代码。历史受遗漏补丁影响的余额/流水必须另行授权只读审计后，采用可审查且可恢复的更正方案，不能自动补扣或冲销。
