# Read models, cache refresh and browser diagnostics

## Read/write boundary

Authenticated indexed read models load only `systemUsers` and tenant settings before the SQL route. Legacy reads keep their explicitly required collections, or the full snapshot when their policy is unknown. Command validation still loads the complete current state once inside the existing serialized write lock; this change does not weaken monetary, inventory or related-document guards.

HTTP method alone does not define this boundary. `POST /api/sales-invoices/:id/outbound/preflight` is read-only but needs current scoped `salesInvoices`, `inventory` and `products`. The shared request policy loads those dependencies without loading finance histories, persisting state, advancing the revision or attaching a mutation state patch. `POST /api/gpu_erp/crm/quick-capture/parse` similarly needs `customers` and `products` (its dedicated audit write stays separate); customer lead preview is a pure calculation needing no business collection.

Outbound confirmation revalidates stock inside the existing serialized transaction and uses the existing reservation/idempotency protections; a successful preview is not an authorization to reuse stale stock. Scanner mode requires at least one code. Manual mode instead requires its existing permission and a non-empty reason, not fake scanner codes. The frontend adapter sends the real empty code list for manual confirmation and preserves real scanner duplicates for server validation; the obsolete synthetic manual marker is removed.

Legacy sales lines with a physical inventory binding follow the same current-card checks: only `已入库` / `已上架`, matching canonical product identity, and each card used at most once. Scanner matches use the card's current ID/SN, not a stale SN copied into an old invoice. Frontend progress/availability helpers mirror these restrictions for feedback; the domain validation remains authoritative. Existing unique-name compatibility for replaced product IDs and completed-outbound idempotency are preserved.

`GET /api/finance/profit-report` requires `finance_reports` and scopes queries to the authenticated tenant and store. It aggregates invoices in PostgreSQL and returns page groups, totals, insight candidates and day-level trends, never historical invoice bodies. Sales and non-operating flows use a single read-only repeatable-read snapshot. Zero is a real value; missing costs/profits remain unknown. Cost and profit fields are projected on the server; hidden profits do not control sort order. Sort keys are allowlisted. Explicit CSV export requests all aggregated groups, not raw invoices.

## Refresh and retry contracts

Document submitters specify affected domains to `refreshErpAfterDocument`. Queries in those domains become stale; only active observers refetch immediately. Hidden tabs and historical filter caches reload when activated. Every business invalidation also expires global-search caches, including cached empty results.

The shared dependency map also expires affected derived read models: returns affect invoice/finance/stock totals; stock affects product counts, inspection queues and candidate pickers. Candidate dependencies target query prefixes, and parent prefixes suppress redundant invalidations. Unrelated domains are not refreshed.

Purchase and sales filter inputs debounce keyword requests. During debounce or placeholder-data transitions, KPI values say `更新中`, not totals from the previous filter.

Return creation holds one idempotency identity for the same submitted payload across response loss and retries. A changed payload gets a new key; confirmed success resets the identity. This lifetime is the mounted form/tab, not a cross-browser persistent draft. Server replay and business validation remain authoritative.

Outbound submission captures the invoice ID, real scanner/manual payload and idempotency key before its first asynchronous request. Preflight and confirmation responses must identify that same invoice; a mismatched preview cannot trigger confirmation, and an unexpected confirmation result cannot be announced as completed. Retrying an unchanged payload keeps its key; changing the invoice, mode, codes or remarks rotates it.

The outbound editor owns its draft and feedback by selection/filter scope and draft version, not invoice ID alone. Switching invoice, keyword or page starts an empty editor, and placeholder rows cannot be selected or submitted. A late success/error for A cannot clear B's input or show A's validation on B; edited input no longer displays obsolete failure feedback. Submitted controls stay locked for their own draft, while a different selected draft remains editable. Background refresh of the same selection retains input. A confirmed hidden tab defers selection reconciliation until activation, and closed tabs and hidden page-clamp effects do not rewrite another page's URL. Domain cache invalidation still occurs for the actually confirmed document.

## Shared camera session boundary

Inspection SN entry, sales outbound and assembly reuse `ErpBarcodeScannerDialog`. Each opening owns its video element, stream and asynchronous detections. Closing/unmounting or deactivating its workspace Tab invalidates that session and stops its tracks. Hiding `ErpDialogShell` alone is not camera cleanup: the scanner effect must also depend on Tab activity. The parent keeps its open intent while inactive, so returning to a kept-alive Tab acquires a fresh stream without clearing form data. Cleanup detaches only the session's own video, never a newer session's element. If camera permission resolves after closure/deactivation, the late stream is stopped immediately. If video playback resolves after closure/deactivation, no detector is constructed. Detection delivery checks ownership and current visibility after its asynchronous result and invokes the current-session callback synchronously; a closed/inactive frame cannot fill a current field or close a reopened dialog. Completions of an inactive session, including failed frames, cannot schedule another animation frame; active focusing errors still retry normally. Ordinary inline callback changes within the same active session still do not restart the camera.

## Inspection mutation ownership

Before asynchronous validation, inspection create and history edit capture the original unnormalized form, the inventory editor scope, and the historical record/version. The validated command is then frozen before the API request. A resolver result cannot submit after its editor has changed. The imperative in-flight guard also rejects rapid duplicate submissions before React publishes its pending state.

Every selection/reset opens a distinct editor. Success only marks/reset the exact submitted editor; failure feedback only belongs to its unchanged form. The pending editor is locked, while another selected item's draft remains editable. Switching/closing a Tab does not cancel an already sent business command or roll it back: its actual domains are still invalidated, but an inactive/unmounted editor never writes the active URL. An owned background success leaves a clean form and reconciles its selection only when its own Tab returns.

A newer inventory deep link remains intact when an old save finishes, including the phone edit view. Registered form identity takes priority over transient URL parameters, so the pending item is not relabeled as another inventory item. Camera callbacks also belong to the current editor and cannot edit an in-flight form.

## Draft image upload ownership

Product, purchase, inspection and income/expense editors reuse a single draft-upload controller behind the existing uploader UI and media API. Each reset/clear creates a distinct draft relation identity and independent serialized queue. Compression, upload results and deletion errors recheck the owning scope after every asynchronous boundary; old editors cannot call the new editor's form callback or publish errors there. Reset and real unmount abort obsolete requests and release each owned Blob preview once. Effect replay retains a mounted editor's previews. Closing a product/finance dialog invalidates its upload scope even though its parent component remains mounted.

Uploads and deletion-relation writes serialize within one draft, with retained URLs resolved when the write runs. A new draft never waits for an unresolved old upload. Queued `local` images block submission immediately, alongside compression, upload and failure states. Submit handlers read the current upload state after asynchronous schema validation rather than a stale rendered flag. Product and finance validation also retain their draft identity so closing/reopening cannot submit an obsolete resolver result.

Hiding a kept-alive workspace Tab is not closing its editor: its own draft continues uploading without changing another page's URL. Closing the Tab cancels its upload ownership. Request cancellation cannot undo a media transaction the server already committed, and does not delete a tenant's assets. Saved documents continue submitting their explicit current URL list through the existing business API; this change neither rewrites historical images nor changes stock/finance facts.

## Purchase quantity boundary

Clearing a filled line's quantity leaves an incomplete draft (`0` rendered as an empty editor), not a fallback physical unit. Invalid/non-integer quantities contribute no units or amounts to the preview; refilling them preserves the chosen product and unit prices. Auto-paid amounts follow the same summary. Submission remains blocked with an explicit quantity reason. Entirely empty spare rows are ignored consistently by form validation, visual error states, summaries and create/full-edit adapters; the default four-row editor and at-least-one-filled-line requirement are unchanged.

`PURCHASE_MAX_PHYSICAL_ITEMS` is the existing 500-item document limit shared by the frontend and backend. It limits the sum of quantities, not only editor/API row counts. Create/full-edit adapters, HTTP DTOs and domain expansion validate the complete batch before allocating physical rows or modifying inventory/financial state. An omitted legacy API quantity still means one; explicit zero, fractions and non-finite values are rejected. Metadata-only historical edits remain available and do not re-expand existing rows.

Batch paste validates each row against the same limit, then checks the exact checked selection plus the current filled form lines before addition. A preview can contain individually valid rows whose combined quantity exceeds 500; reducing quantities or selecting a subset resolves the explicit blocker. Confirmation revalidates current products/capabilities and never silently imports only the valid part of a checked selection. Editing other rows preserves deliberate exclusions, and invalid checked rows can be corrected or deselected. Successful addition removes only the explicitly added rows and never submits a business command itself.

## Redacted diagnostics

The browser batches runtime/API failures and requests slower than 1000 ms to `POST /api/ops/client-events`. Authentication, CSRF, rate limiting and strict bounded DTO validation apply. Diagnostics do not use the ERP write lock or database mutation pipeline.

Only category, allowlisted route template/method, status, bounded duration and UUID request correlation are accepted. Query strings, dynamic identifiers, free-form error messages, stacks, payloads, customer text, tokens and cookies are not transported. The server sanitizes routes again. Deduplication caps the browser at 20 events/minute; transport failure is silent and never retried recursively. Session logout clears the pending buffer.

Structured `client-diagnostics` logs are written to the existing server/PM2 logging sink. Boss-only `GET /api/ops/metrics` includes per-process diagnostic counters; they reset on process restart. Existing log retention/rotation must remain configured operationally. No paid external tracking service is assumed or enabled.

Draft-upload regressions first reproduced three concrete defects: an old deletion failure appeared on the next inspection, closing a Tab during compression still started HTTP, and a new item's upload waited for the obsolete queue. Local native-browser fixtures pass nine inspection cases and 24 product/purchase/income/expense close/reopen cases at 1440/1024/390px, without business writes or whole-page overflow. The repository CLI smoke retains 12 inspection upload-ownership cases at those widths, including completion on a hidden kept-alive Tab. These fixtures intercept API traffic locally; they do not prove production asset cleanup or real database/media-storage writes.

Unit tests cover real QueryClient observer behavior, inactive cache invalidation, retry keys, filter display and telemetry bounds/redaction. Isolated PostgreSQL HTTP tests verify scoped profit aggregation, strict zero, sorting/pagination, authentication and CSRF.

Outbound regression coverage reproduces a database-visible invoice returning `NOT_FOUND` during POST preflight when only users were loaded. It verifies two-item matching, missing/unknown/duplicate scans, manual reasons, tenant/store isolation, no business writes during preview, fresh stock revalidation, actual confirmation and idempotent replay in a disposable database. Parallel scanner/manual previews interleaved with lightweight revision/list reads must retain their own invoice snapshot; canonical and trailing-slash URLs both remain read-only without state patches or revision changes. A cross-policy unit contract locks this distinction across authentication, serialization, persistence and response policies: actual confirmation still enters the serialized write path. Targeted browser fixtures verify two-of-two scanner progress, the exact invoice ID/code/reason/CSRF/idempotency request flow, and no confirmation after server refusal in scanner/manual/rejection cases at 1440/1024/390px. These nine protocol cases also run in the repository browser smoke/CI rather than only in a temporary acceptance fixture.
