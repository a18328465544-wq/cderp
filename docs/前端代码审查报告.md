## 二、🔴 严重问题

### 2.1 `useStoreState` — 单体状态黑洞（1053 行）

**文件**: `src/utils/state.ts`

这是前端架构中最严重的问题。一个 Hook 管理了 22 个独立数据集的 React state、50+ 个 CRUD 方法、5 个聚合计算函数、以及认证/同步/懒加载逻辑。所有消费者通过 `useStoreState()` 获取整个返回对象，导致：

- **过度渲染**：`currentUser` 和 `permissions` 没有用 `useMemo` 包裹（第 981-983 行），每次渲染都创建新对象引用，触发所有消费者的 re-render
- **函数引用不稳定**：`getCurrentUser()`、`getPermissions()` 以及 50+ 个 CRUD 方法都是每次渲染重新创建的新函数
- **违反单一职责**：状态管理 + API 通信 + 聚合计算 + 认证 + 同步调度混在一个函数中

```ts
// state.ts:981-983 — 无 useMemo，每次渲染都是新对象
return {
  // ...
  currentUser: getCurrentUser(),  // ← 新引用，每次都触发消费者 re-render
  permissions: getPermissions(),  // ← 同上
  // ...
};
```

**建议**: 拆分为多个独立 Context 或迁移到 zustand。至少先给 `currentUser` 和 `permissions` 加 `useMemo`：

```ts
const currentUser = useMemo(() => getCurrentUser(), [systemUsers, currentUserId]);
const permissions = useMemo(() => getPermissions(), [systemUsers, currentUserId, currentRole, customPermissions]);
```

### 2.2 前端全量聚合计算

**文件**: `src/utils/state.ts`（`getAccountSummary`、`getInventorySummary`、`getCrmSummary`）

三个聚合函数对全量数据做 O(n) 遍历，且函数体在 Hook 内部（每次渲染重新创建），调用方如果不注意 memo，会造成性能问题：

| 函数 | 遍历数据量 | 每次调用耗时估算 |
|------|-----------|----------------|
| `getInventorySummary` | 全量 inventory | O(n) × 每卡 20+ 字段 |
| `getAccountSummary` | 全量 settlementLedger + accounts | O(n+m) |
| `getCrmSummary` | 全量 customers + followUps + requirements | O(n+m+k) |

这些计算在 Dashboard 和多个 Manager 组件中反复调用。

**建议**: 
- 将聚合计算移到后端 API，前端只做展示
- 或使用 `useMemo` 并仔细管理依赖，避免每次渲染重复计算

### 2.3 CSS `!important` 泛滥（index.css 中出现 60+ 次）

**文件**: `src/index.css`

几乎每条规则都加了 `!important`，形成了一个"谁加得多谁赢"的军备竞赛。这会导致：

- 任何第三方组件或 Tailwind utility 都被强制覆盖
- 需要覆盖默认样式时必须加更多 `!important`
- 调试样式时无法通过 DevTools 快速判断级联关系

```css
/* index.css:155-157 */
body {
  background-color: var(--erp-page-bg) !important;  /* ← */
  color: var(--erp-text-main) !important;           /* ← */
}
```

以及全局的 `table`、`input`、`select`、`textarea` 选择器（第 296-303 行）也用 `!important` 强制覆盖。

**建议**: 逐步迁移到 Tailwind CSS v4 的 `@layer` 机制或提高选择器特异性（用 `.erp-` 前缀类而非全局标签选择器）。

### 2.4 色阶反转 Bug — Indigo 色系方向颠倒

**文件**: `src/index.css`（第 51-61 行）

Tailwind 的颜色体系约定是：**50 = 最浅，950 = 最深**。但 indigo 色阶完全反了：

```css
--color-indigo-950: #f0f4fa;  /* ← 应该是蓝色最深色，实际是最浅的白 */
--color-indigo-900: #e6edf7;
--color-indigo-800: #d4dfed;
--color-indigo-50: #f0f4fa;   /* ← 应该最浅，实际也是白 */
```

这意味着使用 `text-indigo-900` 会意外渲染为浅色，在白色背景上几乎不可见。

**建议**: 修复色阶映射。如果确实需要颠倒的色阶，至少加注释说明为何违反惯例。

## 三、🟡 中等问题

### 3.1 大量 SEO-style 硬编码字符串

整个前端大量使用中文字符串作为状态标识和枚举值，散落在各处：

```tsx
// Dashboard.tsx — 状态比较用字符串
if (card.status === "已售出" || ["已退货", "已报废", "已拆卸", "已组装"].includes(card.status))
// InventoryManager.tsx
const inactiveInventoryStatuses = new Set<CardStatus>(["已售出", "已退货", "已报废", "已拆卸", "已组装"]);
// SalesManager.tsx — 渠道也是硬编码
const [channel, setChannel] = useState<"到店" | "闲鱼" | "抖音" | "小红书" | "B站" | "微信私域" | "同行网店">("到店");
```

同一个 `"已售出"` 字符串出现在至少 6 个不同文件中。如果未来需要国际化或修改状态名，修改成本极高。

**建议**: 将状态、渠道、来源类型等枚举值抽取到 `src/constants.ts`，使用 `as const` 或 enum：

```ts
export const CARD_STATUS = {
  SOLD: "已售出",
  RETURNED: "已退货",
  SCRAPPED: "已报废",
  // ...
} as const;
```

### 3.2 Manager 组件 useState 过多

**文件**: `PurchaseInvoice.tsx`、`SalesManager.tsx`、`InventoryManager.tsx`

每个 Manager 组件管理 20-40 个独立的 `useState`，缺乏表单级别的状态管理：

```tsx
// PurchaseInvoice.tsx — 仅列举一小部分
const [sourceType, setSourceType] = useState<SourceType>("个人回收");
const [supplierName, setSupplierName] = useState("");
const [contact, setContact] = useState("");
const [selectedSourceId, setSelectedSourceId] = useState("");
const [isPaid, setIsPaid] = useState(true);
const [paidAmount, setPaidAmount] = useState<number>(0);
const [unpaidAmount, setUnpaidAmount] = useState<number>(0);
const [expressNo, setExpressNo] = useState("");
// ... 30+ more
```

当用户从列表点击"编辑"跳转回录单页时（`editingInvoiceId` 机制），需要用一个巨大的 `useEffect` 来回填所有字段，容易遗漏。

**建议**: 使用 `useReducer` 将表单状态集中管理，回填时只需一次 dispatch。

### 3.3 autoSyncState 顺序请求而非并行

**文件**: `src/utils/state.ts`（第 461-471 行）

```ts
autoSyncLoadingRef.current = (async () => {
  await requestBackend("/api/state?mode=initial");       // ← 等待完成
  if (productsLoadedRef.current) await requestBackend("/api/products");  // ← 再等待
  if (logsLoadedRef.current) await requestBackend("/api/logs");
  if (financeLedgerLoadedRef.current) await requestBackend("/api/finance-ledger");
  if (settlementLedgerLoadedRef.current) await requestBackend("/api/settlement-ledger");
})().finally(() => { ... });
```

5 个请求完全独立，但用了串行 `await`。在最坏情况下，用户打开所有 Tab 后同步要等 5 个 RTT。

**建议**: 使用 `Promise.all` 并行请求：

```ts
const tasks = [requestBackend("/api/state?mode=initial")];
if (productsLoadedRef.current) tasks.push(requestBackend("/api/products"));
// ...
await Promise.all(tasks);
```

### 3.4 DataTable 写入 localStorage 无节流

**文件**: `src/components/DataTable.tsx`（第 240-245 行）

```ts
useEffect(() => {
  writeDataTablePreferences(resolvedStorageKey, { ... });
}, [columnWidths, columns, hiddenColumnKeys, resolvedStorageKey]);
```

每次拖动列宽（`mousemove` 事件）都会触发 `setColumnWidths` → `useEffect` → `localStorage.setItem`。拖一次列宽可能触发上百次写入。

**建议**: 在 `handleUp`（mouseup 回调）中写入，或在 useEffect 中加 500ms 的 debounce。

---

### 3.5 `mergeRecordsById` 的排序问题

**文件**: `src/utils/state.ts`（第 80-105 行）

```ts
return [...incomingWithoutKey, ...newItems.filter(...), ...replaced];
```

`newItems` 用 `filter` 从 `incoming` 中筛选，而 `replaced` 用 `map` 保持 `existing` 顺序。这导致合并后的数组顺序取决于：先放全新数据，再放已有数据。可能造成排序不一致。

**建议**: 明确排序意图，合并后按业务逻辑（如时间、ID）排序。

---

### 3.6 `requestBackend` 静默吞错

**文件**: `src/utils/state.ts`（第 362-365 行）

```ts
} catch (error) {
  console.warn(`Backend API unavailable for ${url}.`, error);
  return null;
}
```

`autoSyncState` 使用 `requestBackend`（非 `requestBackendStrict`），同步失败时前端无感知，可能导致用户看到过期数据而不自知。

**建议**: 至少区分网络错误和业务错误。连续失败 N 次后在 UI 上提示"数据同步异常"。

---

### 3.7 采购/销售录单页的编辑流程脆弱

`editingInvoiceId` / `editingSalesInvoiceId` 机制依赖 `App.tsx` 中的状态桥接：列表页点击编辑 → `setTab("purchase_add")` + 设置 `editingInvoiceId` → 录单页 `useEffect` 回填表单。

这个跨组件状态传递链有 4 个环节，任一环节出问题都会导致回填失败但无错误提示。

**建议**: 考虑使用 URL 参数（如 `?edit=purchase_xxx`）作为编辑标识，更可靠且支持刷新。

## 四、🟢 轻微问题

### 4.1 import 顺序不一致

**文件**: `InventoryManager.tsx`（第 1-2 行）、`PurchaseInvoice.tsx`（第 1-2 行）、`SalesManager.tsx`（第 1-2 行）

```ts
import { notify } from "../utils/notification";  // ← 在许可证注释之前
/**
 * @license
 * SPDX-License-Identifier: Apache-2.0
 */
```

`notify` 的 import 位于 SPDX 许可证注释上方，而其他 import 在下方。显然是后来插入的。

### 4.2 `isProductsLazyPayloadLoaded` 等判断函数用 `any`

```ts
export function isProductsLazyPayloadLoaded(data: any) {
  return data?.productsLoaded === true;
}
```

应该定义清晰的类型而不是 `any`。

### 4.3 Dashboard 组件过长（822 行）

Dashboard 同时承担了：统计卡片、趋势图表、风险预警列表、热销排行、日志摘要。建议拆分为独立子组件。

### 4.4 表格页的"分页后回顶部"缺失

DataTable 切换页码后数据更新，但页面不会自动滚动到表格顶部。对于长页面（如库存单卡视图），用户需要手动滚回去。

### 4.5 `mutationCountRef` 并发计数是全局的

所有 CRUD 操作共享同一个 `mutationCountRef`，这导致 `isMutating` 只在"有正在进行中的请求"和"所有请求都完成"之间切换——无法区分哪个操作正在 busy。

## 五、✅ 亮点

1. **DataTable 统一底座** — 全站 20+ 表格共享同一个组件，支持列显隐、列宽拖拽、分页、导出、localStorage 偏好持久化，API 设计合理
2. **ui.tsx 设计系统** — `PageShell` / `Card` / `Button` / `Badge` / `Modal` / `StatCard` 等组件统一了全站视觉语言
3. **KeepAlivePanel** — 通过 `memo` 的 `frozen` 跳过非活跃 Tab 的 re-render，非常聪明
4. **CSV 安全** — 防公式注入（`=+-@` 前缀转义）+ BOM 头确保 Excel 正确识别中文编码
5. **sessionStorage 隔离** — 同账号多窗口不互相污染登录态
6. **ErrorBoundary 恢复机制** — "清除冲突缓存并重载" 对普通店员非常友好
7. **权限 UI 闭环** — 从菜单入口到数据脱敏（成本价隐藏、毛利隐藏）全链路
8. **`useDeferredValue` 使用** — SalesManager 和 CrmManager 中搜索输入用了 `useDeferredValue` 减少卡顿
9. **暗色主题迁移注释** — `ui.tsx` 开头明确声明了"逐步淘汰旧深色主题"的迁移路线
10. **14 个测试文件** — 覆盖 CSV、状态合并、Dashboard 计算、菜单权限等核心逻辑
