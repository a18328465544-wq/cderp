# 编辑器提交与草稿图片回归

本地修复覆盖提交保护、既有上传组件的数据恢复，以及退货原单金额与收款来源一致性；不改变页面布局、现有正价退款规则或生产数据。

## 提交保护

商品模板、其他收入、其他支出、采购开单与销售开单使用 `useValidatedFormSubmit`：

- 点击提交时，先记录原始表单内容和编辑器身份，再进行已有的 Zod 校验。
- 真正发起写请求前，核对编辑器身份、原始内容及实时图片状态。校验期间修改了备注、金额或图片时，保留当前内容并要求重新保存。
- 同一编辑器的校验与保存共用同步提交锁。关闭后重新打开的新编辑器不等待旧校验，旧校验也不能提交新编辑器。
- 保存失败继续保留表单与已有错误展示，同时捕获表单提交 Promise，避免未捕获异常。
- 比较原始内容，而不是 Zod 转换后的值，避免 `trim` 等规范化被误判为用户修改。
- 采购、销售 Tab 在校验期间隐藏会取消本次写入，同时释放校验锁；返回后保留原内容，可以重新提交。
- 采购结算账户按提交快照的 ID 查找，避免旧 ID 与新名称混用。保存请求期间禁用表单，避免成功重置清除用户新输入。
- 开单的幂等号在 API 适配后根据实际 DTO 计算：未改变请求内容的重试使用原号，改变内容后使用新号，成功后重置。

采购上传组件从现有表单的图片 URL 一次性初始化。新增图片会保留原有图片，删除只移除目标图片；后续显式清空不会重新载入初始图片。此处的草稿是工作区内存草稿，不宣称支持刷新后恢复。

采购、销售退货沿用原有业务校验，通过 `useReturnSubmission` 共用同步提交锁和编辑器快照。请求只使用提交时捕获的命令，不再从随后渲染的表单闭包读取。保存期间锁定整个表单，已经打开的 Select、Combobox 和单日 DatePicker 也会关闭，解锁后不会自动重开。

退货失败保留草稿和原重试编号；编号在 API 适配后按实际 HTTP 请求内容生成，采购的空格规范化或单件模式忽略的批量字段不会创建新的编号。服务端确认成功后，隐藏的保活 Tab 同样清除已提交草稿，而已关闭的编辑器不会被旧回调修改。

成功提交与读取刷新分开处理。503/网络刷新错误保留已挂载表单及上次参考数据，显示可重试警告；401/403 不使用缓存兜底。刷新异常不能把已经成功的退货标成保存失败，也不能重新锁住下一张单据。库存、付款和结算事实仍由服务端校验。

## 销售出库误报“销售单不存在”

- 出库列表是 PostgreSQL 读模型，预校验则调用领域动作。不能因为方法是 POST，就只加载账号并等待写锁补载；预校验不是写命令，不会进入该路径。其认证快照必须显式包含 `salesInvoices`、`inventory`、`products`，并保持当前企业/门店隔离。
- 预校验的读取、持久化和响应补丁策略共用同一份依赖声明，包括末尾斜杠。预校验不保存业务集合、不扣库存、不生成收款/提成，也不推进业务状态版本；CRM 的 POST 解析预览同样按各自读取依赖处理。
- 正式出库仍在写锁内重读和校验，不信任浏览器的“全部已核验”或前一次预览。库存变为已售出、已退货、已锁定，或型号/实物绑定变化时，整个出库动作拒绝，不部分扣减。
- 一次提交在等待预校验前捕获单据 ID、扫码内容、备注和幂等号。切换单据或 Tab 后的旧响应不能改写新编辑器；未匹配、重复、返回另一张单据等情况不能继续确认。历史中文库存标识原样兼容，不通过修改 SN 来掩盖查单错误。
- 仅有 `sales_outbound` 的仓库账号也能预校验和扫码出库，不要求增加销售列表或财务权限。无人工权限仍返回 403；成功响应与幂等重放都按当前账号裁剪 `data` 和 `stateMerge`，不向仓库账号回传真实成本、利润、资金或其他未授权集合。保留原有金额零遮罩契约，数据库和保存的完整命令结果不被改写。

回归入口：`server/requestStatePolicy.test.ts`、`server/storeSalesOutbound.test.ts`、`server/salesOutboundResponse.test.ts`、`src/features/sales/sales.outbound.attempt.test.ts` 与 `scripts/browser-smoke.mjs`。独立 PostgreSQL 测试 `server/httpIntegration.test.ts` 覆盖真实登录、低权限仓库账号、两件扫码、并发读取、权限拒绝、实时库存变化、落库及幂等重放；运行 `npm run test:backend-http:docker` 只创建临时测试库，完成后自动销毁，不访问生产数据。浏览器脚本的业务响应为本地拦截，UI 协议验证与数据库验证分别报告。

冷快照回归还直接复现旧的仅账号 POST 快照：列表所用的已保存销售单存在，但领域预校验返回 `NotFoundError`。随后按认证依赖加载同一张单据和两件库存，验证普通路径及末尾斜杠路径均返回 `2/2`，且预校验不改变任何业务集合；历史中文库存标识保持原样。

## 日期浮层的可操作边界

- 单日、范围与日期时间控件继续共用 `ErpDateOverlay`。碰撞边界读取现有工作区栏高度和浮层留白 Token，不通过抬高弹窗层级覆盖 Tab 栏。
- 桌面端较高的日期面板以实际可用高度为上限，内容在面板内部滚动；关闭标题栏保持可见。手机仍沿用原有底部面板和可用高度规则。
- 浮层打开期间监听窗口及可视视口变化，旋转屏幕或改变窗口高度后重新计算边界。组件卸载或关闭时移除监听，不改变日期值、路由和业务逻辑。
- `ErpDateOverlay.test.tsx` 核对 Token 边界计算、异常值、服务端渲染和共享样式契约。`scripts/browser-smoke.mjs` 在 1440×900、1440×480、1024×844、1024×480、768×844、768×480、390×844、844×390 八种视口中核对关闭按钮的实际命中位置，并验证滚动后关闭及 Escape，不使用强制点击绕过遮挡。

## 退货金额与原收款来源

- 原单明确记录的 `0` 不再被库存成本或旧草稿金额替代。只有历史采购明细的价格确实为 `null/undefined` 时才沿用库存成本；销售退货不从旧草稿补成交价。
- 保持原有每条退货明细须为有限正数的规则。零价、负价、非法价在前端给出阻塞原因，即使绕过禁用按钮直接提交表单也不发送请求。
- 创建时按原单价格规范化金额；完成时重新校验原单、退货总额和每条已保存明细，变化不一致时拒绝并保留所有集合。不得通过旧退货金额补出新金额。
- 冲销已完成退货前核对原单快照、已保存明细和总额；快照矛盾时停止自动处理。明确记录的零成本、零利润不会被当前库存值替代；还原中途失败会恢复全状态，避免只回滚部分单据或流水。
- 参考查询按查询更新时间合并。较新的选中原单不能被旧列表缓存覆盖；较新的列表刷新也不能被旧选中查询覆盖。
- 新收款记录保存规范化后的业务类型，使收款、账户流水和财务流水一致。历史缺失类型但明确关联销售单的默认销售收款可作为原路退款来源，不重写历史记录，也不把其他收入当作退款来源。

`browser-return-amounts.py` 覆盖桌面、平板、手机的采购单件/多件/整单和销售单件/整单，检查零价、新查询零价、缺失价、正价、负价、非法价以及旧草稿残留金额，共 90 例。后端内存领域测试额外核对创建、完成、冲销拒绝前后全状态一致，以及正常完成和冲销时库存、原单、账户和两套流水同时正确；真实数据库验证仍是独立门禁。

## 退货冲销的后续业务保护

- 已完成退货的冲销先核对每张实物库存的编号、SN、退货后的预期状态和销售单关联，再处理退款流水。重新质检、销售、拆装等后续业务不能被旧退货快照覆盖；批量中任一张库存不符合条件，整张退货单都不变化。
- 即使库存状态被错误重置为待检测，仍核对现有销售明细的库存编号/SN。不能只清空库存的销售关联字段就绕过保护。
- 冲销动作在领域层也要求退货已完成，待处理或已作废记录不能通过旧调用入口重复冲销。直接报废退货的正常冲销继续按原快照恢复。
- 失败回滚恢复原始快照，不走用于导入/重置的规范化流程；无关质检字段、权限或商品库存统计不会因一笔失败操作被顺带调整。
- 已授权、同一幂等号的冲销成功重试先返回原结果，再检查新命令的状态条件。新的幂等号对已作废记录仍返回冲突并释放占用；类型权限和删除权限均在幂等重放之前执行。

`server/storeReturnAmounts.test.ts` 使用本地领域动作复现“退货 → 质检 → 再次销售 → 冲销旧退货”，并覆盖单件/批量、后续拆卸、物理编号/SN 变化、失败原样回滚和重复冲销。`server/routes/returnMutations.test.ts` 核对重放、权限拒绝和新命令状态冲突，不调用真实数据库或写入生产单据。

## 待处理退货的实物归属与接口加载边界

- 原单行号、金额和采购明细临时 ID 只是定位信息，不是实物归属凭证。创建和完成退货时同时核对商品身份、明确保存的库存编号、SN 与原单明细；指定的稳定行 ID 或库存 ID 不存在时，不悄悄改用另一行或同 SN 的另一张库存。
- 采购退货完成前重新核对库存当前状态、原采购单关联及所有有效销售明细。旧待处理退货不能把后来已锁定、已销售或已有后续销售关联的库存改为已退货；即使库存状态和销售关联字段被错误清空，仍通过销售明细阻止覆盖。
- 销售退货核对原销售单已出库、当前库存仍归属于该单以及允许退货的实物状态。历史仅以 SN 关联的销售明细继续兼容，完成时更新实际解析出的库存编号。
- 无 SN 采购按商品身份和原成本匹配，既有正价、缺失历史价格规则不变。创建退货时尚未录 SN、随后正常质检补录 SN 的采购库存仍可合法退货。
- 完成、编辑、作废、冲销和删除的退货类型检查统一在写锁内、业务数据重新加载之后执行。写请求的账号认证快照不再被当成完整业务数据；真实单据不会因此被误报不存在。类型权限及删除权限仍在幂等重放和业务动作之前检查。

`server/storeReturnBinding.test.ts` 覆盖单件/批量错误行绑定、编号/SN/原单关联变化、真实质检后销售、锁定库存、正常完成及冲销和历史兼容；异常拒绝均检查完整状态没有变化。路由测试分别核对五种动作在冷认证快照下的授权重放、类型权限拒绝和真实不存在。

真实 PostgreSQL HTTP 回归使用临时测试库，验证同价不同商品被拒绝、待处理退货创建后出现后续销售、错误重置库存后的再次拒绝、正常退款及幂等重放。失败前后对比业务集合、账务事实和业务状态版本，成功重试不重复入账。运行入口为 `npm run test:backend-http:docker`，不连接生产数据库。

## 退货响应与参考数据的权限边界

- 完整状态、单集合、分页退货列表、写入结果及 `stateMerge` 使用同一套服务端字段裁剪。销售、采购退货的单件和批量原单快照同时处理成本、利润字段，不依赖前端隐藏。
- 采购退货金额本身能反推出原采购价；无成本权限时，金额、明细金额、供应商抵扣和现金释放金额沿用零遮罩契约。销售退货保留业务退款金额，但不因此开放成本、利润、账户余额或历史资金记录。
- 退货参考查询按当前账号可操作的退货类型加载数据。显式请求未授权类型返回 403；省略类型时也不会顺带加载另一种原单。退货菜单权限不等于完整财务权限：账户候选可用于选择，但无账户菜单权限时不返回余额，付款记录要求对应付款菜单权限。
- 六种退货写动作及其成功幂等重放都在 HTTP 边界按当前权限重新裁剪；收回成本权限后，原成功结果不会继续暴露成本，收回退货类型权限后直接拒绝。数据库和完整幂等缓存仍保留原始账务事实，不因权限裁剪修改金额或重复入账。
- 返回补丁只允许退货领域涉及的集合，删除回执也按可见集合过滤。旧缓存中的全状态、任意附加字段和其他退货单编号不直接透传。

`server/returnPermissionProjection.test.ts` 覆盖单件/批量快照、成本与利润的独立权限、资金字段、补丁与删除回执、权限变更后的缓存重放、无认证账号及异常结果格式，并核对原状态和缓存未被修改。真实 PostgreSQL HTTP 回归覆盖已登录低权限账号、完成和重放、分页与参考查询、类型越权、同一会话权限收回，以及账户、退款和业务状态版本未因裁剪改变。该验证仅证明已覆盖的退货入口，不代表其他业务模块的所有返回路径已经完成权限审计。

## 售后维修结案与费用落账

- 维修/检测结案不等于销售退货。明确保存的零退款不再被销售价替代；历史缺失退款在非退货结案中也默认零。明确的零维修费用不被旧 `loss` 替代，只有缺失值才兼容历史字段。正式退货仍必须使用销售退货链路。
- 售后费用命令失败时恢复工单、库存、客户/供应商、账户、付款、两套流水和日志的原始快照，非法金额或没有可用结算账户不能留下部分已结案状态。
- 维修结案的持久化补丁包含确切关联的付款、账户、账户流水和财务流水，与工单在同一事务中落库；不只保存工单里的付款编号，也不全量保存无关账户/流水。
- 已结案工单不得直接变更状态、退款或维修金额；需要正式财务更正。相同成功命令的幂等重放不重复扣款，新的请求不能通过改成拒绝来绕过冲销。
- 售后工作区和写入回执按当前成本/利润权限裁剪相关库存与销售单。工单维修费/退款金额作为业务操作信息保留，但无付款权限时不返回付款记录编号，无相应财务权限时不返回账户或流水补丁。内部缓存和数据库仍保存完整事实。
- 权限裁剪不增加售后账号对完整库存、销售列表或财务页面的权限。真实不存在/其他企业门店的售后工单在申请幂等号和写入之前拒绝；工作区查询仍直接读取当前门店数据库，不依赖暖缓存。

回归入口：`server/storeAftersalesAmounts.test.ts`、`server/aftersalesResponse.test.ts`、`server/routes/aftersalesMutations.test.ts` 和 `server/requestStatePolicy.test.ts`。`server/httpIntegration.test.ts` 在临时 PostgreSQL 库中验证真实登录、仅售后权限的工作区与结案、120 元维修费用的完整落账、明确零退款、跨企业/门店拒绝、原销售单金额不变、重放与当前权限、终态改账拒绝和业务版本一致性。

本地修复不会删除或更正历史生产流水。如果历史工单曾受零值回退或补丁遗漏影响，应在明确授权后只读核对来源工单、账户和两套流水，再走可审查的财务更正/数据恢复方案；不能仅因工单显示已完成就自动补扣费用或自动冲销。

## 售后原单、实物绑定与后续业务保护

- 新售后必须关联当前门店的有效原销售单和真实已售库存。库存编号优先定位，SN、商品身份及原销售明细共同核对；指定编号不存在时不改用同 SN 的另一件，商品同名也不是实物归属凭证。待出库、已作废或已有其他销售单关联的原单不能登记售后。
- 客户与商品显示信息从已核对的原单和库存生成，不使用客户端传入的冒名标签。客户稳定编号不得与原单矛盾；缺少历史客户编号时仅使用唯一姓名关系，不批量增加所有同名客户的售后计数。
- 同一实物在同一销售归属下只能有一张未结案售后。并发使用不同幂等号登记仍受写锁内重新加载和领域校验保护；相同已成功命令继续返回原结果，不误报重复登记。
- 完成或拒绝之前重新核对原单、实物编号/SN、原单明细和当前售后/维修状态。已经正式退货、再次质检或再售的库存不能被旧工单改回已售出，也不能生成旧工单的新维修费。拒绝操作同样不能跳过实物核对。
- 新增和结案只改确切的库存编号，持久化补丁也只包含该件实物。历史重复 SN 不导致另一张库存一起进入售后或一起恢复已售出；重复拒绝旧工单不会释放后来新工单的库存。
- 原单、实物和资金关联字段不可通过处理状态动作重新绑定。无编号的历史工单仅在 SN 唯一且原销售单关系能够完整证明时解析并补充编号；有错误编号或多个候选时拒绝，不自动纠正、删除或收费。
- 正式退货并再售后，旧归属的历史工单不能阻塞新客户的售后。前后端活动工单匹配共用原单与实物规则，不仅比较 SN；旧记录保持原样，新工单仍核对新原单，旧工单不能因新工单恢复售后状态就重新获得处理权。

`server/storeAftersalesBinding.test.ts` 覆盖错误原单/客户/明细、重复工单、重复 SN、正常拒绝、历史兼容、关联字段变更，以及真实“售后 → 正式退货 → 质检 → 再售”的旧结案拒绝。错误分支对比完整业务状态。

临时 PostgreSQL HTTP 回归额外验证低权限登录、不同幂等号并发创建仅成功一次、补丁只含目标库存、真实销售退货后旧完成/拒绝均冲突，以及账户、付款、两套流水、日志和业务状态版本不发生额外改变。随后通过真实质检、再销售和出库接口验证新客户售后能够登记、结案，旧工单保持原样，且不能借新工单的售后状态重新获得处理权。原有售后成本/利润和资金权限投影回归继续执行。本轮不改页面布局，也不连接或清理生产历史数据。

## 销售编辑草稿版本保护

- 销售单创建时产生 `recordVersion=1`；无版本的历史记录在读取/比较时按 1 处理，不批量改写历史数据。更新接口要求整数 `expectedRecordVersion`，在写锁内加载最新状态后先比较，再执行任何库存、往来或收款修改。版本过期返回 `409 CONFLICT`，细分原因为 `STALE_SALES_RECORD`，不会留下半份修改。
- 编辑、收款/收款冲销、出库、销售退货/退货冲销和关联客户/供应商信息更新共同推进版本。退货冲销恢复原商品与金额但不恢复旧版本，避免过期草稿重新变为有效。重复已成功的幂等命令不再次推进版本或产生重复资金流水。
- 编辑器保存初始化草稿时的版本；后台查询刷新不能将旧输入自动绑定到最新版本。成功后更新草稿版本并清除已保存状态，冲突保留输入并提示先保留修改、重新打开单据核对，不误导用户仅刷新商品候选后强行重试。切换单据身份重新初始化对应表单。
- 前端完整编辑和仅备注/快递编辑均传递版本，后者不夹带商品或资金字段。版本由服务端生成，客户端不能直接覆盖 `recordVersion`。

回归：`server/storeSalesVersion.test.ts` 验证并发编辑、历史无版本、真实收款/冲销、出库、单件/批量退货/冲销和客户改名，并对拒绝分支比较完整业务状态。临时 PostgreSQL HTTP 用两次并发 PUT 验证仅一份成功、幂等重放不产生新事实、最新版本可从列表读取、收款/出库后旧编辑被拒绝，账户、流水、实物归属及全局业务版本保持原样。`scripts/browser-sales-edit-version.py` 在 1440、1024、390 宽度验证完整/受限两种编辑、后台刷新后的冲突保留输入以及连续成功保存；所有浏览器业务 API 均为本地模拟。

该契约上线必须同步发布前后端：旧客户端不传版本会被明确拒绝，不能通过省略版本绕过保护。本轮没有生产部署，也不自动修正历史覆盖记录。采购和质检有各自既存的版本边界，不能据此宣称所有单据并发链路已经统一完成。

本轮最终本地结果（2026-10-04）：完整回归 1322 项，其中 1300 通过、22 个数据库场景在普通测试环境跳过；这些数据库场景已通过临时 PostgreSQL 单独执行，22/22 通过、0 跳过。浏览器 12 个场景通过，无页面异常；lint、前后端类型/服务端测试类型检查和本地前后端构建通过。出库只读核验冷权限快照与当前数据库库存读取回归在同一批数据库验收中再次通过。这些结果不代表生产部署或生产资金写入验收。

## 采购编辑、供应商抵扣与子流程版本保护

- 采购编辑、付款/付款冲销、单件/批量采购退货及冲销、关联客户/供应商信息更新推进 `recordVersion`。质检新增/修改、扫码入库/移库和批量库存调整同步推进关联采购版本。一个命令涉及多件实物时，同一采购单只推进一次；未命中或被拒绝的扫码不推进版本。
- 实物关联以明确的 `purchaseInvoiceNo` 为准，没有结构化归属时才兼容历史备注中的完整进货单号。错误结构化归属不回退到旧备注，前缀相似的单据不被顺带更新，不为孤立库存创建虚构采购单。
- 质检与库存写流程在写锁内加载采购依赖，事务补丁只持久化确切关联的采购记录；开放库存接口同样加载并保存父单版本。只读工作区不为此额外预加载全部采购单。写路径仍沿用现有集合加载机制，不宣称已经改为按父单 ID 的定向 SQL 查询。
- 采购草稿绑定初始化版本，后台刷新不会用最新版本为旧输入背书。成功保存后重置已保存表单并更新版本；过期保存返回 `409 / STALE_PURCHASE_RECORD`，保留输入，提示先复制需要保留的修改、重新打开原单核对。完整编辑与仅备注/快递编辑都受此保护。
- 采购未付款严格为 `总成本 - 实际现金付款 - 已使用供应商抵扣`。总成本 2000、抵扣 500、现金付款 1500 时欠款为 0；冲销这笔现金付款后欠款恢复为 1500、状态为部分付款，不能重新出现已抵扣的 500 欠款。补付超过真实剩余金额被拒绝，账户、供应商往来与两套流水不产生部分修改。
- 内部持久化完整金额，HTTP 增量响应按当前认证账号投影。仅有质检/库存权限的账号不收到关联采购单或日志，库存成本和商品参考价按权限隐藏；批量调整的 `data` 与 `stateMerge` 使用相同边界。商品参考价格投影同时覆盖既有全量与集合响应，不能因补丁新增关联数据扩大可见范围。
- 质检、库存和客户/供应商变化失效相关采购详情缓存；仅刷新活跃查询，隐藏的草稿不会被失效动作直接覆盖，也不启动未打开页面的读取。

本地回归覆盖：`server/storePurchaseVersion.test.ts`、`server/purchaseRecordVersion.test.ts`、DTO/权限投影/读取策略/缓存失效/适配器/冲突提示测试，以及临时 PostgreSQL 的并发 PUT、幂等重放、抵扣补付/冲销、质检新增/修改、批量移库、开放接口移库和持久化详情读取。拒绝分支比较库存、往来、账户、两套流水、审计及全局业务版本，不仅检查状态码。`scripts/browser-purchase-edit-version.py` 在 1440、1024、390 宽度覆盖完整/受限编辑、后台刷新冲突保留输入和连续保存，共 12 例；浏览器接口全部为本地模拟。

发布仍须同步前后端。本轮不连接生产，不运行数据迁移，也不自动纠正历史账务；历史受抵扣计算或过期覆盖影响的记录须另行授权只读审计，再确认更正方案。该验证边界不等于所有单据、历史数据和生产资金写入已全部验收。
